# Scraper reliability audit

Reviewed 5 November 2026 on `feature/scrapper` at `5f226d2`. Findings below follow the source paths and existing tests. The intermittent behavior still needs reproduction against a running browser and PostgreSQL with controlled provider delays.

## Findings

| Priority | Finding | Evidence and effect |
| --- | --- | --- |
| P0 | Stop can succeed while Import stays disabled | [Scraper page](../frontend/src/app/scraper/page.tsx#L290) uses one `working` flag for collection and import. Stop flips a ref, which prevents another wave only after the current `Promise.all` settles. The server can already have committed `REVIEW_READY` while Import and Continue remain disabled. Stop also awaits secondary list and review refreshes before clearing its own spinner. |
| P0 | Late fetches can be accepted after a stop and resume | [Run advance](../backend/routers/scraper.py#L1340) claims an attempt with an expiration, commits, then fetches. Completion checks the run and attempt statuses but has no claim identity. If Stop requeues the attempt and Resume claims it again, the original response can observe the new `RUNNING` state and write against the replacement claim. Expired leases present the same race. Client waves also publish results after the stop flag changes and choose a summary using timestamps, so stale progress can briefly reappear. |
| P0 | Import and normalization depend on one HTTP request finishing | [Import endpoint](../backend/routers/scraper.py#L1743) commits `IMPORTING`, ingests a batch, links it to the run, commits `NORMALIZING`, then awaits normalization. [Normalization](../backend/services/normalization.py#L94) iterates jobs and can await FX lookups. The client waits for selection sync, the full POST, and follow-up refreshes. [The API wrapper](../frontend/src/lib/api.ts#L775) supplies no default deadline. Request interruption can strand an intermediate status. The external batch ID supports replay, but retries in active states lack a distinct worker claim, so a second tab can attempt work already in flight. |
| P1 | The source UI renders several different outcomes as a blank list | [Source panel](../frontend/src/app/scraper/page.tsx#L730) maps optional data and shows zero active when data is absent. Loading, 403, transient errors, and a successful empty inventory are visually indistinguishable. Queries start before owner access resolves. Source actions have no per-row pending guard, and failed health checks can commit `FAILING` or `COOLDOWN` while the UI keeps its previous data because it refreshes only on success. |
| P1 | Source reads write, and health checks hold a lock during provider I/O | [Source listing](../backend/routers/scraper.py#L444) syncs seeds and commits before reading. Concurrent first reads or run creation can race on inserting the same seed. [Revalidation](../backend/routers/scraper.py#L547) holds a row lock and database connection while awaiting a provider. Contention is plausible with a [five-connection pool and two overflow connections](../backend/database.py#L1747). Production timing is needed to establish how often this contributes to the empty list or slow controls. An empty provider response is also treated as failure, although an accessible, valid board can have zero jobs. |

## Fix checklist

The first implementation pass separates collection, stop, and import waits in the browser. Stop publishes the acknowledged run before refreshing history, and obsolete browser collection requests are cancelled. The backend uses the existing attempt counter as a claim generation for collection and discovery. A controlled API test covers stop, resume, and late completion from the old claim.

On 5 November 2026, the full migration chain and PostgreSQL model check passed on an isolated local PostgreSQL instance. An Edge browser test against the real app used simulated providers with a slow response and HTTP 429. It verified that another board completed during the wait, the retry remained scheduled after Stop & review and reload, and the resumed run finished with three sightings and two unique candidates. The delayed response from the original claim did not stage a candidate. The test exposed an invalid scraper session URL and stale dashboard polling during active collection. The session URL and polling were corrected before the passing run.

Import now saves the accepted selection, linked batch, and completed normalization as separate durable checkpoints. Each stage and its writes commit together. An Edge test against PostgreSQL verified a concurrent request during normalization, browser reload, rollback after an injected failure, and successful retry with the same batch ID. Live employer-provider checks and unattended execution remain open.

- [ ] Make the persisted run state authoritative. Keep the existing Stop & review action as a resumable pause. On acknowledgement, show staged results and enable review actions immediately. Give collection, stop, selection, import, and source actions independent pending states. Scope selections and partial confirmation to the current run. Show why a control is unavailable beside it.
- [ ] Fence collection and source-discovery claims with unique claim IDs. Commit only if the claim still owns the attempt. Requeue unfinished claims on stop, keep committed results, and reject late writes. Use a run generation or monotonic revision to ignore stale browser responses. Add bounded fetch deadlines and backoff when all slots are claimed. A stale worker must leave the replacement claim untouched.
- [ ] Make Source Inventory read-only and seed with an idempotent upsert outside GET. Gate owner requests on resolved auth. Render loading, denied, failed with Retry, stale with a refresh error, empty, and populated states. Keep rows visible during refresh. Show checking, healthy with jobs, reachable with zero jobs, failing, disabled, and cooldown with the next eligible check time. Run network checks outside locks and fence result writes against intervening edits or checks.
- [ ] Persist import as an operation with a fixed selection snapshot, partial confirmation, and one stable batch key. Return acknowledgement quickly, then show queued, importing, normalizing, imported, or retryable failure with counts and the batch link once linked. Evaluate reuse of the existing processing claim and retry protocol in [operations](../backend/routers/operations.py). Verify the deployed worker can actually execute both stages before switching the UI to polling.
- [ ] Reconcile interrupted import by batch key. Resume from the last committed stage, reclaim expired work, and serialize active retries. Show selection-save failures before submitting. Bound browser waits and refresh status after uncertain outcomes. Keep ranking as an explicit subsequent action.
- [ ] Add structured timing and error codes for lock wait, provider fetch, pause acknowledgement, import, and FX normalization. Correlate by request, run, attempt, and operation IDs. Set initial staging acceptance targets of pause acknowledgement within two seconds with a deliberately slow provider and visible import acknowledgement within two seconds for a representative batch. Verify those targets under concurrent load before treating them as service guarantees.

## Regression and acceptance tests

| Scenario | Expected result |
| --- | --- |
| Three provider calls remain blocked while the owner stops the run | Stop returns within the staging target, review opens, and Import becomes available after selection and partial confirmation. Late fetches cannot add jobs to the paused run. |
| Stop, resume, and reclaim the same attempt before the original fetch returns | Only the replacement claim can write candidates, counters, health, or checkpoint. Repeat for expiry, cancel, source discovery, and two tabs. Use PostgreSQL for lock semantics. |
| Reload, close the tab, lose the network, or switch runs during a mutation | Reopen to the correct persisted state and reason. Old results cannot change the active run or borrow its selection or confirmation. A slow refresh cannot keep a completed action spinning. |
| First-time concurrent source requests, owner versus member, empty inventory, and backend 5xx | Unique seed rows, clear permission and empty states, retained cached rows on refresh failure, and a visible Retry. |
| Health check races with another check or an edit, or provider returns zero jobs | One current result wins. The row reflects persisted health after success or failure and preserves the latest edit. Zero jobs and provider failure display differently. |
| Drop the connection before ingest commit, after batch commit but before linkage, and during normalization | Reload or retry reaches the correct stage and creates exactly one batch. Concurrent retries converge, and normalization failure is actionable. |
| Selection write fails, no valid jobs are selected, or a partial run lacks confirmation | Import is blocked with a specific reason. Successful retry imports exactly the confirmed selection, normalizes to INR, and opens the batch for manual ranking. |

The existing [scraper API tests](../backend/tests/test_scraper_api.py) cover sequential stop, resume, partial confirmation, and import. The [PostgreSQL test](../backend/tests/test_scraper_v2_postgres.py) checks model and migration compatibility. Add coordinated race tests and a browser workflow with delayed or failed requests to cover the gaps above.
