A model is not “deployed” in one step.

JEDI separates the physical model files from the database record that authorizes their use. That separation is the safety system.

1. What the manifest does

manifest.json is the bundle's identity card. It records the model version, contract versions, feature schema, required runtime versions, and a SHA-256 checksum for every artifact. On load, JEDI recomputes those hashes. A missing or changed file stops the model before prediction.

manifest → verify files → load pipelines → golden prediction → READY

2. What “Register embedded bundle” does

The button does not upload or train anything. The files were already packaged into the FastAPI Vercel service by includeFiles. Registration first loads and verifies that checked-in bundle, then copies its manifest and artifact hash into a PostgreSQL ModelVersion row as an inactive candidate.

3. Why checks and activation are separate

The deployment check compares the live runtime identity with the database candidate. Activation is permitted only after they match. Ranking runs can then pin an exact model version, and rollback means activating a retained version rather than replacing history.

4. What failed in this deployment

Vercel starts main:app. JEDI's health router imported services.model_runtime, while registration imported backend.services.model_runtime. Python treated them as two modules and created two singleton runtimes. The health copy loaded successfully; the registration copy resolved its packaged filesystem independently and reported a missing manifest.

The fix has two parts: make the entrypoint import every component through one canonical backend.* namespace, and resolve relative bundle paths from either the Python package root or Vercel's service working root. Health, registration, checking, and ranking then share one loader that can find the packaged files.

Retrieval check

Does registration upload the .joblib files?

No. Vercel packages them during deployment; registration stores their verified identity and metadata in PostgreSQL.

Why can a schema-valid manifest still fail?

Its listed file may be absent, a checksum may differ, a dependency version may differ, or the golden prediction may fail.

What does activation change?

It changes which verified registry version future ranking runs pin. It does not mutate the model artifact.
